# Stalwart PIM Client 仕様書

Stalwart サーバー専用のメール・予定・連絡先クライアント。
migration kit の標準 PIM アプリとして開発する。

- 実装: Python + Flet(デスクトップ)
- ライセンス: AGPL-3.0(リポジトリ本体と同一)
- リポジトリ: migration kit 内に配置(`stalwart-pim/`)
- 対象 OS: Debian(第一)、他 Linux、Windows、macOS
- 前提サーバー: **Stalwart 0.12 以上**。CalDAV / CardDAV は 0.12(2025-06)で
  追加された機能であり、これより古いサーバーは対象外とする

## 1. 目的

Google Workspace が担っていた三機能(メール・カレンダー・連絡先)を、
Stalwart サーバー + 本アプリの組で完全に置き換える。

前提となる構造上の決定:

1. **接続先は Stalwart のみ。** 汎用メーラーではない。
   世界中のサーバーの方言に対応しない。この前提が実装規模を桁で下げる。
2. **真実はサーバー側にある。** クライアントは薄い窓に徹する。
   ローカルキャッシュは高速化のための読み取り専用コピーであり、
   同期の主体ではない。
3. **既製品(Evolution)は併存する。** 本アプリは置き換えを強制しない。
   migration kit では Evolution を「今日から使える答え」、
   本アプリを「箱の標準 PIM」として二段構えで提供する。

## 2. 作らないもの

実装しない機能。追加の議論はこのリストの変更から始める。

- HTML メールの作成(閲覧は簡易表示のみ)
- **送信 MIME の組み立て**(JMAP の `Email/set` create に委ねる。
  本アプリは送受信とも MIME に一切触らない — §3.1)
- メールフィルタ・振り分けルール(サーバー側 Sieve に委ねる)
- ラベル・タグ・スター等の独自メタデータ
- 全文検索エンジン(検索 UI は持つが、実行はサーバーの JMAP query に
  委ねる — §4.1)
- 繰り返し予定(RRULE)のクライアント側解釈(サーバー展開に委ねる)
- オフライン編集・送信キュー
- 複数アカウントの同時表示(1 起動 1 アカウント。複数必要なら
  `--profile` で分離して複数起動 — §5.6)
- プラグイン機構
- IMAP / POP3 / Exchange 対応
- 通知デーモン・常駐(起動時と手動更新のみ)

## 3. プロトコル

### 3.0 前提の実機検証(最初に行う)

本仕様は Stalwart の次の 2 機能に構造ごと依存している。

- `calendar-query` REPORT の **expand**(繰り返し予定のサーバー展開)
- **sync-collection** REPORT(RFC 6578。DAV の差分取得)

これらは実装詳細ではなく前提条件である。開発段階 1(§6)の接続テストで
実機確認し、期待通り動かない場合はこの仕様書に戻って設計を改める。
コードで回避しない。

### 3.1 メール: JMAP (RFC 8620 / 8621)

- Stalwart のネイティブプロトコル。JSON over HTTPS。
- IMAP は使わない。IMAP の方言対応こそ汎用メーラーの複雑さの源泉であり、
  Stalwart 専用と決めた時点で不要になる。
- 認証: Basic 認証(アプリパスワード)。将来 OAuth が必要になったら追加。
- エンドポイント発見: `https://{server}/.well-known/jmap`
- 使用するメソッド:
  - `Mailbox/get` — フォルダ一覧
  - `Email/query` + `Email/get` — 一覧・本文取得・検索(`filter: {text: ...}`)
  - `Email/set` — 既読・削除(= ゴミ箱フォルダへの移動)・下書き保存・
    送信メールの作成
  - `EmailSubmission/set` — 送信。**`onSuccessUpdateEmail` で送信済み
    フォルダへの移動と `$draft` 除去を同時に指定する**(Stalwart は
    送信済みへの複製を自動では行わない。クライアントが指示しなければ
    送信済みフォルダは空のままになる)
  - `Blob/upload` / ダウンロード URL — 添付
- MIME は組まない・読まない。送信は `Email/set` create で Email オブジェクト
  (宛先・件名・`textBody`・添付は blobId 参照)を JSON で組み立てる。
  受信も `Email/get` の `bodyValues` で構造化済みの本文を受け取る。
  返信ヘッダ(`inReplyTo` / `references`)も Email プロパティで指定する。
  転送時の添付は受信メールの blobId をそのまま参照する(再アップロード不要)。
- 下書き: 作成画面の「下書き保存」で `Email/set` create(`$draft` +
  下書きフォルダ)。送信時は同じ Email を `EmailSubmission/set` に渡す。

### 3.2 予定: CalDAV (RFC 4791)

- 実体は HTTP + XML。`httpx` と `xml.etree.ElementTree` で直接実装する。
  caldav 等のラッパーライブラリは使わない(最小依存・最大標準)。
- エンドポイント発見: JMAP と対称に `https://{server}/.well-known/caldav`
  → `current-user-principal` → `calendar-home-set` の順にたどる。
- 使用する操作:
  - `PROPFIND` — カレンダー一覧の発見
  - `REPORT calendar-query` — 期間指定での予定取得
  - `PUT` — 予定の作成・更新(iCalendar を送る)
  - `DELETE` — 削除
- 繰り返し予定は calendar-query の expand を必ず指定する。
  サーバーが展開した個別の予定インスタンスを受け取る。
  クライアントは RRULE を一切解釈しない。
  この一点がカレンダー実装の複雑さの大半を消す。
- **expand の結果は表示専用である。** 展開済みインスタンスを PUT で
  書き戻してはならない(マスターの破壊・意図しない上書きになる)。
  編集・削除は次の経路に限る:
  - 編集: 元リソースを href で GET し直し、対象プロパティのみ書き換えて
    PUT する。round-trip 保持(下記)はこの経路で効く
  - PUT には **`If-Match`(ETag)** を付け、他クライアントとの同時編集を
    競合として検出する(上書きせずエラー表示)
  - **RRULE を含む予定は初版では閲覧のみ。** 編集・削除ボタンを無効化する
    (DELETE はリソース単位であり、「この日だけ消す」つもりが全回消える)
- タイムゾーン方針: **DTSTART / DTEND は UTC で書く。VTIMEZONE は生成しない。**
  終日予定は `VALUE=DATE`。expand の応答も UTC で返るため往復で整合する。
  繰り返し予定を作らない初版では、これが最も単純で正しい。
- iCalendar の生成・解析は最小限の自前実装とする。
  扱うプロパティ: `SUMMARY` / `DTSTART` / `DTEND` / `LOCATION` /
  `DESCRIPTION` / `UID` / `ATTENDEE` / `ORGANIZER`。それ以外は保持して
  そのまま返す(round-trip 保証。理解しないものを壊さない)。
- ics 招待メールの受理: メール画面で `text/calendar` 添付を検出したら
  「予定に追加」ボタンを表示し、PUT で自分のカレンダーに登録する。
  その際 **`METHOD:` 行は除去する**(残すと他クライアントが招待として
  再解釈する)。出欠返信(iTIP REPLY)は初版では実装しない。

### 3.3 連絡先: CardDAV (RFC 6352)

- CalDAV と同じ構造。発見も対称(`/.well-known/carddav` →
  principal → `addressbook-home-set`)。
  `PROPFIND` / `REPORT addressbook-query` / `PUT`(`If-Match` 付き) /
  `DELETE`。
- vCard 3.0 のみ対応。扱うプロパティ: `FN` / `N` / `EMAIL` / `TEL` /
  `ORG` / `NOTE`。それ以外は round-trip 保持。
- メール作成画面の宛名補完は、**起動時に取得したメモリ上の連絡先一覧**から
  前方一致で行う。キャッシュ導入後(§6 段階 6)はキャッシュがこの一覧の
  供給源になるが、補完の正しさはキャッシュに依存しない。

## 4. 画面構成

3 画面 + 設定。左端に固定のナビゲーションレール。

### 4.1 受信箱 (mail_screen.py)

```
┌──────┬──────────────┬────────────────────┐
│ nav  │ フォルダ一覧   │ [検索ボックス]      │
│      │  受信箱       │  メール一覧         │
│ 📧   │  送信済み     │  ┌──────────────┐  │
│ 📅   │  下書き       │  │ 差出人 / 件名  │  │
│ 👤   │  ゴミ箱       │  │ 日時          │  │
│ ⚙   │  (Stalwart の │  └──────────────┘  │
│      │   実フォルダ)  │  選択で本文を       │
│      │              │  下ペインに表示      │
└──────┴──────────────┴────────────────────┘
```

- 一覧はサーバーから 50 件ずつページング取得。
- 検索ボックス: 入力確定で `Email/query`(filter)をサーバーに投げ、
  結果を一覧に表示する。ローカルでは検索しない(§2)。
- 本文表示: text/plain を優先。text/html しかない場合は
  タグ除去したテキストを表示し、「ブラウザで開く」ボタンで
  一時ファイルを既定ブラウザに渡す。アプリ内に WebView は持たない。
  ブラウザに渡す HTML は **`<script>` を除去し、リモート画像等の外部参照は
  遮断する**(開封トラッキング防止)。外部参照の読み込みは
  「画像を読み込む」の明示操作でのみ許可する。
- 操作: 返信 / 全員に返信 / 転送 / 削除(ゴミ箱へ移動) / 添付保存。
- 作成画面: 宛先(補完付き) / 件名 / 本文(プレーンテキスト) / 添付 /
  **下書き保存**(§3.1。下書きフォルダから開いて再開できる)。

### 4.2 予定表 (calendar_screen.py)

- 表示は月表示と当日リストの 2 種のみ。週表示は作らない。
- 月表示: 各日のセルに予定の件名を最大 3 件表示。クリックで当日リストへ。
- 予定の追加・編集はダイアログ 1 枚: 件名 / 開始 / 終了 / 終日フラグ /
  場所 / メモ。
- 繰り返し予定は閲覧のみ(§3.2)。詳細表示に「繰り返し予定(編集は
  他クライアントで)」と表示し、編集・削除を無効化する。
  作成は初版では実装しない。実運用で必要が観察されてから追加を検討する。

### 4.3 連絡先 (contacts_screen.py)

- 左: 検索ボックス + 一覧(FN 昇順)。右: 詳細表示・編集フォーム。
- 検索・一覧はメモリ上の連絡先一覧に対して行う(§3.3)。
- 編集項目は 3.3 の対応プロパティのみ。

### 4.4 設定 (settings_screen.py)

- サーバー URL / ユーザー名 / アプリパスワード。
- 接続テストボタン: JMAP well-known・CalDAV PROPFIND・CardDAV PROPFIND の
  3 点を順に叩き、結果を表示する。あわせて **expand と sync-collection の
  対応を確認し(§3.0)**、非対応ならサーバーのバージョン更新を促す
  メッセージを出す。
- 認証情報の保存は OS のキーリング(`keyring` ライブラリ)。
  平文ファイルには置かない。キーリングが利用できない環境
  (Secret Service 未起動の Linux 等)では、その旨と対処
  (gnome-keyring の導入等)を案内して起動を継続する(保存はしない)。

## 5. アーキテクチャ

### 5.1 構成原則

- 自己完結ウィジェット。画面 1 枚 = ファイル 1 枚。
- 宣言的 UI(Flet 1.0)。画面は `@ft.component` の関数コンポーネントで、
  状態は `use_state` としてその画面の中に持つ。`page.update()` は
  呼ばない——状態の**置き換え**が再描画を導く。再描画の要否は同値比較で
  決まるため、オブジェクトの書き換えではなくコピーして置き換える。
  状態管理ライブラリは別途入れない。
- ダイアログ(作成・編集フォーム)は開いている間だけの命令的な島として
  よい。フォーム値は入力コントロールから読む(制御された入力にしない)。
- Service 層がプロトコルを完全に隠蔽する。
  画面は dict と dataclass しか受け取らない。
- コメントは「なぜ」だけを書く。「何を」はコードが語る。

### 5.2 ファイル構成

```
stalwart-pim/
├── main.py                 # 起動・--profile 解決・ナビゲーション・画面切替
├── services/
│   ├── jmap_service.py     # JMAP セッション・メール操作
│   ├── caldav_service.py   # カレンダー操作(expand 指定を含む)
│   ├── carddav_service.py  # 連絡先操作
│   ├── cache.py            # SQLite キャッシュ(読み取り高速化専用)
│   └── models.py           # dataclass: Mail, Event, Contact
├── screens/
│   ├── mail_screen.py
│   ├── calendar_screen.py
│   ├── contacts_screen.py
│   └── settings_screen.py
├── pyproject.toml
└── README.md               # セットアップ 3 手順で書く(初回起動時の
                            # 実行体ダウンロードに触れる)
```

### 5.3 依存関係

```toml
[project]
dependencies = [
  # Flet は 1.0 系 API(0.70 で全面刷新された線)を採用する。
  # デスクトップ実行体は desktop extra(初回起動時にダウンロードされる)
  "flet[desktop]>=0.86,<1.1",
  "httpx",     # HTTP クライアント(JMAP / CalDAV / CardDAV 共通)
  "keyring",   # 認証情報の OS キーリング保存
]
```

これ以外の依存は追加しない。JSON・XML・SQLite・日時は
すべて標準ライブラリで処理する(MIME 処理は存在しない — §3.1)。

### 5.4 キャッシュ (cache.py)

- SQLite 1 ファイル(プロファイルのデータディレクトリ内 — §5.6)。
- テーブル: `mails(一覧表示用ヘッダのみ)` / `events` / `contacts` /
  `sync_state(各リソースの state 文字列)`。
- 起動時: キャッシュを即表示 → バックグラウンドでサーバーに state を
  問い合わせ → 差分があれば取得して置き換え → 再描画。
- JMAP は `Email/changes`、DAV は `sync-collection` REPORT で差分取得。
  差分取得に失敗したら全件取り直す(壊れたら捨てて作り直せる、が
  キャッシュの定義)。
- 書き込みは常にサーバーへ直接行う。成功レスポンスを受けてから
  キャッシュを更新する。ローカル先行の書き込みはしない。

### 5.5 エラー処理

- ネットワーク断: 画面上部にバナー表示。キャッシュにあるものの閲覧は
  継続する(メールは**一覧のみ**。本文はキャッシュしないため読めない)。
  書き込み操作(送信・予定追加等)はエラーダイアログで明示的に失敗させる。
  裏で再送しない(送信キューは作らない — §2)。
- 認証失敗: 設定画面へ誘導。
- 編集競合(PUT の `If-Match` 失敗): 「他のクライアントで変更されています。
  再読み込みしてやり直してください」と表示し、上書きしない。
- サーバーエラー(5xx): レスポンス本文をそのままログファイルに記録し、
  ダイアログには「サーバーエラー。ログ: <パス>」とだけ出す。

### 5.6 プロファイル

- データディレクトリ: `~/.local/share/stalwart-pim/<profile>/`
  (cache.db・設定・ログ)。既定プロファイル名は `default`。
- `--profile <名前>` で切り替える。キーリングのサービス名にも
  プロファイル名を含め、アカウントごとに完全に分離する。
- これが §2「複数アカウントは複数起動」の実体である。プロファイルを
  分けない複数起動は同一アカウントの 2 窓として動く(書き込みは常に
  サーバー直行なので破綻しない — §5.4)。

## 6. 開発の順序

各段階が単独で動く状態を保つ。

1. **設定 + 接続テスト** — 3 プロトコルの疎通確認だけのアプリとして完成。
   **expand・sync-collection の前提検証(§3.0)をここで済ませる**
2. **メール閲覧** — 受信箱の一覧・本文表示・検索(読み取り専用で完成)
3. **メール送信** — 返信・作成・添付・下書き
4. **連絡先** — 閲覧・検索 → 追加・編集(宛名補完もここで接続。
   補完はメモリ上の一覧から — §3.3)
5. **予定表** — 月表示の閲覧(expand) → 追加・編集(If-Match) →
   ics 招待の受理
6. **キャッシュ** — 最後に入れる。1〜5 はキャッシュなしで正しく動くこと。
   キャッシュは正しさに関与しない層であることを構造で保証する

## 7. 検証

- 検証環境: 本番 Stalwart とは別に、検証用 Stalwart(0.12 以上)を
  コンテナで立てる(migration kit に compose 定義を含める)。
- 各 Service はアプリなしで単体実行できる形にする
  (`python -m services.jmap_service` で受信箱一覧を標準出力に出す等)。
  プロトコル層の検証を UI から切り離す。
- 実運用検証: 開発者自身が日常メールを本アプリに切り替えて
  2 週間使う。観察された不足のみを追加する。

## 8. migration kit 内での位置づけ

- Evolution: 「今日から使える既製の答え」としてマニュアルに残す
  (CalDAV / CardDAV / メールを 1 本でネイティブに扱えるため。
  DESIGN.md の対応表が挙げる Thunderbird は本決定に合わせて
  Evolution に更新する)。
- 本アプリ: 「箱の標準 PIM」。Stalwart とセットで配布する。
- 本アプリ自体が教材である。「メールアプリすら Markdown 仕様 + AI 実装で
  作れる」ことの実例として、本仕様書もアプリと同じリポジトリで公開する。
